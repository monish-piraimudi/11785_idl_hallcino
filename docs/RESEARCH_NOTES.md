# Research notes: Jacobian lens and Gemma 4 12B

Research checked against the primary sources below on 2026-11-07. The upstream Jacobian-lens dependency is pinned in pyproject.toml to commit 581d398613e5602a5af361e1c34d3a92ea82ba8e (package jlens 0.1.0). The official model card's config.json resolved to revision 43c9d014b231474fa7212dbb48a762566c2b255d; local checkpoints can differ and are always inspected at runtime.

## What the recorded vectors mean

At source block l and token position t, h[l,t] is the complete text decoder block output before the text model's final RMSNorm. The lens matrix J_l estimates the mean Jacobian from that source residual to a chosen target residual:

    J_l = mean_over_prompts mean_over_valid_source_t sum_over_valid_target_tprime>=t
          d h[target,tprime] / d h[l,t]

For each fixed valid source position, the reference injects a one-hot cotangent at the same output dimension at every valid target position. Causality makes earlier targets contribute zero; the backward pass sums same-position and future-position effects. It then averages the resulting gradient over valid source positions. The reference excludes the first 16 and final positions by default, and averages per-prompt matrices equally across prompts. Do not confuse summing target-position contributions with averaging source positions.

j_transport = J_l h[l,t] is stored as dense float32. With row-vector storage, the implementation computes h @ J_l.T; the upstream matrix has [target_dimension, source_dimension] orientation. This is a first-order transport into the target residual basis, not the original hidden state, PCA, a random adapter, a logit lens, or a tuned lens.

The readout applies the checkpoint's final text RMSNorm and output head once. For Gemma 4 12B, it also applies configured final logit softcapping once. The output array retains top-k logits and token IDs for inspection; softmax is unnecessary for ranking and the stored values are logits. The dense transported vector retains information that the small top-k diagnostic omits.

The paper's formal J-space is a different downstream construction: vocabulary-indexed J-lens vectors form an overcomplete set; at sparsity level k, J-space is the union of cones generated by sparse nonnegative combinations of those vectors. Recovering a point's J-space component requires sparse decomposition (the paper uses gradient pursuit). Hallucinot does not perform that decomposition, and j_transport must not be labeled an exact sparse J-space projection.

## Estimator and calibration cost

Hallucinot uses jlens.fit and jlens.jacobian_for_prompt without changing the estimator. It sets the target to the final text decoder block output (before final RMSNorm). With that target, valid source indices are strictly less than the final block index. On the official 12B configuration, the text stack has 48 blocks, so source layers are 0 through 46; layer 47 is the target and is rejected as a source. No requested layer is silently dropped.

Per prompt, the reference runs one forward pass and ceil(d_model / dim_batch) backward passes. Each backward uses a batch of independent output-dimension cotangents; increasing dim_batch reduces launch count but replicates the prompt graph and increases peak activation memory. At the official hidden width 3,840, dim_batch=8 means 480 backward passes per prompt. For 1,000 prompts that is 1,000 forwards and 480,000 backward passes, before skipped short prompts. The CLI reports these counts, the selected matrices' fp32 size, and approximate peak temporary-plus-final lens disk use. It cannot predict exact GPU memory or runtime because backend kernels, checkpoint quantization, sequence lengths, and device placement matter.

The paper's default calibration corpus is about 1,000 pretraining-like sequences of 128 tokens. Smaller corpora can be useful for iteration, but data/calibration/tiny_calibration.txt is only a debug fixture and is inadequate for scientific conclusions. Keep a separate corpus; never calibrate on QA references or held-out evaluation examples.

## Gemma 4 structure and alignment boundary

The official google/gemma-4-12B-it configuration identifies Gemma4UnifiedForConditionalGeneration, model_type=gemma4_unified, and text config gemma4_unified_text: 48 text blocks, hidden size 3,840, vocabulary 262,144, BF16 in the unquantized card, and final logit softcap 30.0. In Transformers 5.16.0, the 12B wrapper contains the text stack at model.language_model; the stack has embed_tokens, layers, and norm. The vision and audio input projections are separate components. The selected hook is model.language_model.layers.<index> output. That is after the complete decoder block and before model.language_model.norm.

The official 12B config says num_kv_shared_layers=0; the decoder's 48 blocks use a mix of sliding and full attention. The CLI discovers the actual loaded jlens layout, prints each path, and checks the config's layer count against the module list. It does not load the paired google/gemma-4-12B-it-assistant MTP draft model. Generation uses one token at a time with the target model's KV cache, so speculative decoding and multi-token prediction are absent.

Gemma 4's processor supports enable_thinking=False. The tool passes it explicitly and does not add <|think|>. The 12B template may include an empty thought channel when thinking is disabled. If a thought channel is nevertheless generated, token IDs and rows are retained and reasoning-channel body tokens are masked separately from answer tokens.

The collector calls the full model for the prompt, chooses one greedy next token, then feeds that token back through the KV cache to capture the state used to choose the next token. Thus the activation predicting token s is different from the activation after consuming token s. Row 0 uses the last prompt position. Each row also saves the source token ID, source position, generation step, source-is-prompt flag, attention mask, token ID, and special/channel-control/EOS/end-of-turn/reasoning/answer masks.

## FP8 and what remains unverified

The loader uses dtype="auto" and reads the local checkpoint's quantization_config; it does not cast the whole model. It reports the backend config, observed parameter dtypes, per-hook activation dtype/device/shape, and exposed KV-cache dtype. J_l and transport math are float32; the model's own output normalization/head retain their checkpoint module behavior.

Inference support does not prove activation-gradient support. Calibration freezes all base parameters but must retain the graph from source block outputs through later blocks. Before fitting, Hallucinot runs a real autograd preflight through the loaded checkpoint and fails with the quantizer and next diagnostic step if gradients are unavailable. It never silently swaps to BF16. If an explicitly calibrated BF16 copy is later used with an FP8 collection checkpoint, compatibility is rejected by default. The opt-in flag only records a user validation note; the researcher must independently validate that approximation on held-out prompts before relying on it.

No Gemma checkpoint or suitable GPU is available in this workspace. The machine has an RTX 4060 Laptop GPU with 8 GiB VRAM, and the original Python 3.12 environment had no PyTorch. Therefore no Gemma FP8 load, quantizer identification, gradient preflight, calibration, or trajectory run has been completed here. The exact target checkpoint's quantization format, backend, activation/KV precision, gradient behavior, and FP8 lens fidelity remain machine-specific checks.

Other unverified assumptions: that the selected FP8 backend preserves the expected block-output graph and module hooks; that the wrapper's chat template and decode path on the target Transformers build return the same text-only inputs; and that dense Jacobian transports on Gemma 4 12B carry features predictive of hallucination. The paper's results are principally on Claude models. Collection success is not evidence of classifier utility.
